# Security

Lilly is a single-user program on your own computer. This page states what it defends against, how, and where the limits are.

## What it protects

* Your files outside the folders you share.
* Your private data (files, notes, memory) from being sent to a model you did not allow.
* Your API keys.
* Your computer from actions a model, or a web page a model read, talks it into.
* The interface from other websites and other people on your network.

## Controls

**Access.** Lilly binds to `127.0.0.1` only. Signing in needs a random access token kept in `~/.lilly/config/access-token` (mode 0600). A successful sign-in sets a signed, expiring session cookie (HttpOnly, SameSite=Strict, `__Host-` prefixed and Secure over HTTPS). Failed sign-ins are throttled (8 per minute). *Sign out everywhere* and *replace token* are in Settings → Security.

**Every request.** The decision is made inside each endpoint's `guarded()` wrapper, so a new route cannot forget it. State-changing requests must be same-origin and carry a CSRF token derived from the session. The `Host` header must be loopback or a name you added under allowed hosts (defeats DNS rebinding). Bodies over 1 MiB are refused. Responses carry a strict Content-Security-Policy (no inline script), `nosniff`, no-referrer, frame denial, and `no-store` on API pages.

**Policy floor** (applies in every access mode, including Open):
* tools marked forbidden never run;
* credentials are never shown to an agent, and SECRET data never leaves the device;
* a task that has read untrusted content (the web) needs approval before it changes anything or sends private data out (Meta's "Rule of Two");
* file paths must resolve (after `..` and symlinks) inside a shared folder, and never inside Lilly's own data folder, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.kube`, `~/.config/gcloud` or the Keychain folder, whatever case or accents the path is spelled with (`.LILLY` is `.lilly` on a Mac);
* writes use a temporary file in the target directory with `O_NOFOLLOW`, never overwrite unless asked, and replace atomically.

**Approvals.** Bound to the hash of the exact step, single-use, expire after 15 minutes, and the waiting task holds the only copy of what will run, so approving cannot change it.

**Taking permissions away.** A task keeps the permissions and mode its agent had when it started, so changing an agent is not left to "the next step". When an agent is edited to allow less (research, memory, files, computer or chat turned off, or a stricter mode) or is deleted, every unfinished task of that agent is cancelled at once, including a step that is running or waiting for approval, and the task says "stopped because the agent's permissions were changed" (or "the agent was deleted"). Allowing more, or editing the name, instructions, skills, pet, look or model, stops nothing. Other agents' tasks are untouched. *Settings* work differently: folders you share, limits and browser rules apply at the next step, and a module you switch off is gone from the next step on (a step of a task already running that then needs it fails), but a step that is already running is not interrupted; use *Stop all* for that. A task's mode is fixed when it starts, so a lower default mode applies to tasks started afterwards.

**Notes written by agents.** `notes.write` creates a note in a space or replaces an existing one, and always asks, in every mode: the approval card shows the title and the whole text, which is capped at 8,000 characters so that nothing is cut from view, and what is saved is exactly the approved text, stored as plain text and never as markup (it is bound to the same hash as any other step). Creating never overwrites. Editing must name the revision `notes.read` showed; if the note has changed since, nothing is saved and the agent is told to read it again. The tool needs the `notes` module and the agent's memory permission. An agent cannot delete notes.

**Models.** A model marked *local* must be an Ollama server on this computer or an address on a private network (127.x, 10.x, 172.16–31.x, 192.168.x, Tailscale 100.64–127.x, `::1`, `fc00::/7`); a host name other than `localhost` is refused because a name can be pointed anywhere, and so is any other provider. Ollama traffic uses its own client that ignores proxy settings and never follows redirects. A remote model sees PERSONAL data only through a grant you give (once, for a task, or standing for a time); it never receives SECRET data. A model that may train on inputs needs a grant even in Open mode. Skills are hash-pinned data and cannot raise a step's risk.

**MCP connections.** An MCP server is a program you add; Lilly treats it as untrusted code that returns untrusted text. It is started without a shell, in its own process group, in an empty temporary folder, with only `PATH`, `HOME`, `LANG`, `TMPDIR`-style basics, the plain settings you typed and the secret values you stored for it (never Lilly's own variables, keys or proxy settings). It starts when first needed and stops after it has been idle (default 10 minutes); everything it started is killed with it. Before any of its tools can be used you review the exact list it offers (names, descriptions, schemas) and choose, tool by tool, *reads only*, *changes things* or *reaches outside*; the choice is pinned to a fingerprint of that list. After every start, and whenever the server says its tools changed, the list is compared with what you approved and a difference refuses the call until you review again. Its tools appear to the planner as `mcp.<server>.<tool>`, are always treated as leaving the computer and as untrusted (a task that used one needs approval before it changes anything, as with web content, even when the call failed), and what they return carries the label you gave the server (default personal, so a cloud model needs your permission to see it). Requests a server makes of Lilly (sampling, roots, elicitation) are refused. Messages, tool counts, descriptions, schemas and results are size-capped. Changing how a server starts withdraws its approval. Secret values live only in the key store under names Lilly generates; the API cannot read or write any other name through the connections screens.
**Computer control.** Off by default (module `computer`) and allowed per agent. Computer actions follow the configured approval mode: MANUAL asks, AUTO permits policy-safe actions, and OFF suppresses prompts for actions that policy allows. Hard denials and exact per-action confirmation requirements always remain. Persistent ComputerRuntime captures event-driven frames, rejects stale frame IDs, grounds semantic targets through AX/DOM then vision then coordinates, and verifies a fresh observation after each action. Commands are run as an argument list (no shell) in a shared folder, with a minimal environment, a time limit and a 64 KB output cap; privilege escalation, shutdown, disk and boot tools are refused, as are `rm` of `/` or `~` and `dd` to a device. Output of commands is treated as untrusted.

**Browser.** Off by default (module `browser`). The agent drives your installed Chrome, Chromium, Edge or Brave through its local debugging port in a separate profile that is created empty for each browser start and deleted when it quits, so it holds none of your sign-ins, history or extensions. The browser is one process in its own process group, with one tab per task; tabs close after two quiet minutes, the browser quits after the idle time in Settings (default 5 minutes), and Stop all and shutdown close it. Every request a page makes (not only the first) is checked before it leaves: http(s) only, and only public addresses (the same rule as web fetching); downloads are refused and pop-ups are closed. The agent acts on numbered targets that repeat an element's role, name and site (`s3.e7 button "Sign in" @example.com`); an action is refused if the snapshot is out of date (the page changed, or anything was done since) or the element is no longer what the target says, so what you approve is what is clicked. Passwords and card fields are never typed by the agent, files cannot be chosen, and submitting a form is its own tool. Page text and everything the browser returns is untrusted, so the task is tainted and later changes outside the browser ask as usual. How much asks is your choice: *ask every time* (default), *ask for risky things* (plain clicking goes ahead; sending, buying, deleting, signing in and every submit or key press still ask) or *trusted sites only* (everything goes ahead on the sites you list). A task has an action budget (default 40). Browser steps never run beside other steps.

**System 1 and Laya.** Before expensive model calls, typed System-1 decisions may classify the task, select a model tier, route capabilities, select a tool family, decide verification depth and detect loops or injected instructions. The full policy-filtered capability catalog remains available; ranking cannot hide a required tool. Laya can recommend only code-supplied options. It cannot allow, approve or widen anything, and deterministic policy never imports its decision. A decider that errors, times out, is not installed, is unsure or answers outside the list is skipped and the safe fallback is used. Every question is logged with a redacted bounded summary and per-task call/token caps.

**Side-by-side steps.** Steps of one plan may run at the same time only if every one of them is a plain read (lowest risk, no confirmation, not the model call) and policy would allow it even in the worst case, where the task has already read everything the unfinished steps before it could teach it. Policy only gets stricter as a task learns more, so allowed in the worst case means allowed in the plan's own order. Everything else waits for all earlier steps, runs alone and holds back the later ones, so approvals still come one at a time and each is tied to the exact action.

**Laya (optional add-on).** `lilly laya install` (run by `install.sh` unless `--no-laya`, or from Settings or the command) creates a separate Python environment under `~/.lilly/addons/laya`, installs the pinned `laya` release from wheels only (no build scripts run), and downloads the model from one pinned Hugging Face commit over HTTPS, one file at a time, keeping a file only if its size, git id and (for the weights) SHA-256 match the reviewed values in `src/lilly/decide/laya_pins.py`. Only safetensors and JSON are fetched, nothing that can run code on load. The model runs in its own process with offline mode set, two threads, and no knowledge of Lilly's keys or settings; it answers only with a choice and a confidence. It loads when first needed, is let go after about 90 seconds of quiet, answers one question at a time, and is left alone for the rest of the session if it is too slow three times in a row.
**Routines.** A routine is a saved request that starts a normal task on a schedule. It runs under its agent's mode and permissions, so every rule above applies unchanged: actions that need approval wait in Approvals and expire after 15 minutes, while computer control follows MANUAL/AUTO/OFF with the same hard policy floor. Extra guard rails: at most 20 routines, a routine never starts while its previous run is still going, a missed run happens once rather than once per missed slot, five failures in a row pause it, a routine whose agent was deleted pauses instead of falling back to the default assistant, and Stop all pauses every routine.

**Chat apps (Telegram).** Off until you enable it. Lilly only asks Telegram for messages (outbound long polling): no port is opened. The bot token is kept in the key store and never returned by the API. A person is linked by a one-time 8-character code (10 minutes, burned after five wrong tries) sent to the bot in a private chat; after that only that numeric account id is answered, and strangers get no reply. Messages are size-capped and rate-limited per person, and start tainted tasks that reach only agents you marked reachable from chat. Approval buttons show the exact action and carry a single-use id; computer-control approvals and anything that is not a plain step are approved only in the app. An answer that used personal data or more stays in the app unless you turn on private replies. A polling offset is saved before a message is handled, so a message is never handled twice.

**Devbox.** Off by default (module `devbox`) and allowed per agent that may use files. Commands run in a container with no network, no Docker or Podman socket, no extra privileges (all capabilities dropped, no new privileges), a read-only root with a small scratch area, caps on CPU, memory and processes, and one bind mount: the shared folder you choose. The shared folder must be inside a folder you shared with Lilly, must not be a link out of it, must not contain anything Lilly keeps private (its own data, your keys), and may not contain characters that change what a mount means. The box is the only way a command touches that folder: everything in it can be changed or deleted by the box, so use a folder made for the purpose. Output is untrusted and counted as private. The image is downloaded only when you press the button. A command that times out, is cancelled or is stopped by Stop all removes the box so nothing keeps running.

**Live view.** Read-only pictures of an agent's browser tab, only on request from a signed-in interface. It cannot click or type, never opens a tab and never keeps the browser awake.

**Web fetching.** Only http(s). Every address a name resolves to must be public (blocks loopback, private, link-local, CGNAT/Tailscale, multicast, and IPv6 forms that hide them: mapped, NAT64, 6to4, Teredo). The fetch connects to the checked address, so a second DNS answer cannot swap in an internal one. Redirects are re-checked and sizes capped.

**Secrets.** API keys live in the system keychain; if there is none, in a `0600` file and the interface says so. Keys are never returned by the API, never written to settings (settings containing key-like fields are rejected) and are redacted from logs. What keeps Lilly's own secrets (access token, cookie secret, key file, database, settings) from a model: file, data and devbox tools can only reach shared folders and never Lilly's data folder, even when a parent folder is shared, through a link, or with another spelling of the name (`tests/integration/test_secrets.py`); the devbox refuses a shared folder that contains it; web and browser requests go only to public addresses, so Lilly's own page on this computer is out of reach; an MCP server starts with a clean environment and only the secrets you stored for it; a model provider's failure reaches the task only as a description built from its status code, and an unexpected error as one generic sentence (details go to the log, where keys are redacted). What does not: nothing scrubs tool output for secret-looking text (that would corrupt data and give false assurance), so a secret you paste into a note, a memory or a shared file is data like any other; an approved `computer.run` command runs as you and can read anything you can; and a program you add as an MCP server is not sandboxed.

**Integrity.** Events are hash-chained per task; Activity → Verify record recomputes the chain. Backups are `0600`; the data folder is refused if group- or world-writable.

## Limits you should know

* **The devbox was tested against a stand-in for Docker, not a real engine.** The container arguments have not been run on a real Docker or Podman by the author. Network isolation relies on the engine's `--network none`. A container is not a virtual machine: a flaw in the engine could let code out, and the shared folder is fully writable by the box.
* **Telegram was tested against a fake server only.** Messages pass through Telegram's servers, which can read them. Message length and button data limits are from Telegram's documentation as the author remembers it.
* **Routines only run while Lilly is running** and do not wake a sleeping computer. Start Lilly at sign-in with `./install.sh --login-item`.
* **Computer control is only as safe as the command you approve.** The refusal list is a guard rail, not a sandbox: an approved command runs with your account's permissions and can change anything you can. Read the "Exactly what will run" panel before approving. The macOS-specific paths (`open`, notifications) have not been run on a Mac by the author.
* **An MCP server runs as you.** Lilly controls what it is told and what it may use, not what the program itself does: it can read any file your account can, including the key file when there is no keychain, and use the network. Add only programs you trust. There is no sandbox around it.
* **Local malware is out of scope.** Anything running as you can read `~/.lilly` and, without a keychain, the key file. Lilly does not defend against a compromised computer.
* **Free model tiers may log or train on what you send.** Lilly marks such models and asks before sending them private data, but cannot control a provider's policy. Use a local model for sensitive material.
* **Prompt injection cannot be eliminated**, only contained: the policy above limits what an injected instruction can do, and the Rule of Two puts a person in the loop for the dangerous combination. Read approvals before accepting them.
* **Over Tailscale** your tailnet members' devices can reach the sign-in page; they still need the token. Do not publish Lilly with Funnel or a public tunnel.
* **A private-network model is only as private as that network.** Lilly cannot tell a machine at home from a shared office network; use the address of a machine you control.
* **The browser's network check is made before the request, not at connection time.** A hostile site that answers a public address to Lilly's check and an internal one to the browser's own lookup moments later (DNS rebinding) is not stopped by it. Turn the module off if that matters to you. The auto-approval modes trust your judgment of the site, and the "risky" word list is a heuristic: a button named "OK" can still do anything. Take-over (you typing a password in the agent's browser) is not built; live view is read-only. The browser has been run only on Linux; Mac and Windows paths are written but unverified.
* **Laya's install is not independently verified.** The pins were read from the Hugging Face listing and have not been checked against a downloaded copy by the author; the first real install is that check and it refuses on any mismatch. The packages Laya needs (PyTorch and others) are installed from wheels at whatever versions pip resolves, not pinned by hash. The model needs roughly 2 GB of memory while loaded and does not install on computers that PyTorch has no wheel for (for example Intel Macs on current PyTorch); there the install stops with a plain message and Lilly works the same without it.
* **Not independently audited.** The controls above are covered by automated tests (`tests/integration/test_api.py`, `tests/unit/`), not by a third-party penetration test. The macOS-specific pieces (Keychain, launchd) have not been run on a Mac by the author.

## Reporting

Report a vulnerability privately to the maintainer of your copy of Lilly rather than in a public issue.
